# 합의수 그림형 모의문제

영어 용어는 영어(한글 뜻) 형태로 병기했다. 정답과 해설은 맨 아래에 모아 두었다.

## 문제

1. Atomic read/write register(원자적 읽기/쓰기 레지스터)만으로 consensus object(합의 객체)를 구현하려 한다. 프로토콜 트리에서 다음과 같은 임계상태가 있다고 하자.

```text
        S  ← critical state(임계상태), bivalent(양쪽 결정 가능)
       / \
 A.read B.read
     /     \
 0-valent 1-valent
```

`A.read`와 `B.read`가 각각 0-valent(0으로만 결정 가능), 1-valent(1로만 결정 가능)로 상태를 바꾸는 것이 불가능한 이유를 쓰시오.

2. 같은 상황에서 두 스레드의 다음 step(단계)이 같은 register(레지스터) `x1`에 대한 write(쓰기)라고 하자.

```text
        S  ← critical state(임계상태)
       / \
 A.write(x1, v0)   B.write(x1, v1)
       /                 \
   0-valent           1-valent
```

두 write(쓰기)가 위처럼 서로 다른 결정 상태를 만들 수 없는 이유를 쓰시오.

3. 이번에는 두 스레드가 서로 다른 register(레지스터)에 write(쓰기)한다고 하자.

```text
        S
       / \
 A.write(x1, v0)   B.write(x2, v1)
       /                 \
   0-valent           1-valent

단, x1 != x2
```

`A.write(x1, v0)`와 `B.write(x2, v1)`가 서로 다른 결정 상태를 만들 수 없는 이유를 쓰시오.

4. 다음 그림은 atomic read/write memory(원자적 읽기/쓰기 메모리)의 합의수(consensus number)가 1임을 보이는 흐름이다. 빈칸 A에 들어갈 핵심 결론을 쓰시오.

```text
1개 스레드 consensus(합의)
    가능
     |
     v
2개 스레드 consensus(합의)
    read/write만으로는 불가능
     |
     v
consensus number(합의수) =  ______A______
```

5. CAS(compare-and-swap/compare-and-set, 비교 후 교환)를 이용해 consensus(합의)를 구현하려 한다.

```text
초기 상태

decision = EMPTY

        decision
           |
        EMPTY
```

```cpp
int decide(int my_value)
{
    CAS(&decision, ______A______, ______B______);
    return ______C______;
}
```

빈칸 A, B, C를 채우고, CAS의 consensus number(합의수)가 무한대인 이유를 쓰시오.

6. FIFO queue(선입선출 큐)를 이용해 두 스레드 A, B의 consensus(합의)를 구현하려 한다.

```text
초기 queue(큐)

front
  |
  v
[ WIN ] -> [ LOSE ]
```

각 스레드는 자기 제안값을 저장한 뒤 dequeue(꺼내기)를 한다.

```cpp
proposal[id] = my_value;
token = queue.dequeue();

if (token == WIN)
    return ______A______;
else
    return ______B______;
```

빈칸 A, B를 채우고, FIFO queue(선입선출 큐)의 consensus number(합의수)가 2인 이유를 쓰시오.

7. 다음 두 실행을 비교하시오.

```text
실행 1
A가 먼저 dequeue

queue: [ WIN ] -> [ LOSE ]

A gets WIN
B gets LOSE
결정값: ?
```

```text
실행 2
B가 먼저 dequeue

queue: [ WIN ] -> [ LOSE ]

B gets WIN
A gets LOSE
결정값: ?
```

실행 1과 실행 2에서 각각 어떤 값으로 합의되는지 쓰시오.

8. FIFO queue(선입선출 큐)가 2개 스레드 합의는 가능하지만, CAS처럼 무한대 합의수를 갖지는 못하는 이유를 한 문장으로 쓰시오.

9. Universal construction(범용 구성)에서 공유 객체의 상태를 log(로그)로 저장한다고 하자.

```text
head
 |
 v
[ NODE0 ] -> [ NODE1 ] -> [ NODE2 ] -> ...

각 NODE:
+----------------------------+
| Invocation invoc           |
| Consensus decideNext       |
| NODE* next                 |
| int seq                    |
+----------------------------+
```

`Invocation invoc`에 저장되는 데이터가 무엇인지 쓰시오.

10. 같은 구조에서 `Consensus decideNext`가 필요한 이유를 쓰시오.

```text
여러 스레드가 같은 NODE 뒤에 자기 NODE를 붙이려고 함

               candidate A
              /
[ current ] --
              \
               candidate B

current.decideNext.decide( ? )
```

`decideNext`가 없으면 어떤 문제가 생기는지 설명하시오.

## 정답 및 해설

1. read(읽기)는 공유 메모리 상태를 바꾸지 않는다. 따라서 `A.read` 또는 `B.read` 하나만으로 다른 스레드가 볼 수 있는 상태가 달라지지 않으므로, 같은 임계상태 `S`에서 한쪽은 0-valent, 다른 한쪽은 1-valent로 갈라지는 결정적 변화가 될 수 없다.

2. 같은 register(레지스터)에 대한 두 write(쓰기)는 마지막 write만 남는다. 예를 들어 `A.write(x1, v0)` 뒤에 `B.write(x1, v1)`를 하면 최종적으로 `x1`에는 `v1`만 남는다. A의 write는 덮여 사라지므로, 그 실행은 B의 write만 한 실행과 구별하기 어렵다. 그런데 한쪽은 0-valent, 다른 쪽은 1-valent라고 하면 같은 상태에서 다른 결정을 해야 하므로 모순이다.

3. 서로 다른 register(레지스터)에 대한 write(쓰기)는 순서를 바꾸어도 최종 메모리 상태가 같다. 즉 `A.write(x1, v0)` 뒤 `B.write(x2, v1)`와 `B.write(x2, v1)` 뒤 `A.write(x1, v0)`의 결과는 둘 다 `x1 = v0`, `x2 = v1`이다. 순서가 구별되지 않는데 결정값이 달라져야 한다면 모순이므로, 두 write가 임계상태를 각각 0-valent와 1-valent로 가를 수 없다.

4. A = 1. Atomic read/write memory(원자적 읽기/쓰기 메모리)는 1개 스레드 합의는 가능하지만 2개 스레드 wait-free consensus(무대기 합의)는 구현할 수 없으므로 consensus number(합의수)는 1이다.

5. A = `EMPTY`, B = `my_value`, C = `decision`. CAS(비교 후 교환)는 `decision`이 아직 비어 있을 때만 첫 번째 성공자의 값을 넣는다. 나머지 스레드는 CAS에 실패하더라도 이미 정해진 `decision`을 읽어 같은 값을 반환한다. 스레드 수가 몇 개든 이 방식이 가능하므로 CAS의 consensus number(합의수)는 무한대다.

6. A = `my_value`, B = 먼저 WIN을 가져간 스레드의 proposal(제안값). FIFO queue(선입선출 큐)는 두 스레드 중 누가 먼저 왔는지를 `WIN/LOSE` 토큰으로 구분할 수 있다. 먼저 온 스레드는 자기 값을 결정하고, 나중 스레드는 먼저 온 스레드의 값을 따르면 되므로 2개 스레드 consensus(합의)가 가능하다. 그러나 3개 이상 합의까지 보장하지 못하므로 합의수는 2이다.

7. 실행 1에서는 A가 WIN을 얻으므로 A의 proposal(제안값)으로 합의한다. 실행 2에서는 B가 WIN을 얻으므로 B의 proposal(제안값)으로 합의한다. 중요한 점은 LOSE를 얻은 스레드도 WIN을 얻은 스레드의 값을 따라가므로 둘이 같은 값을 반환한다는 것이다.

8. FIFO queue(선입선출 큐)는 두 스레드 사이에서 첫 번째 승자를 구분하는 힘은 있지만, CAS처럼 임의 개수의 스레드 중 최초 승자를 하나의 atomic conditional update(원자적 조건부 갱신)로 확정하는 능력은 없기 때문이다.

9. `Invocation invoc`에는 해당 NODE(노드)가 log(로그)에 기록하려는 객체 연산의 호출 정보가 저장된다. 예를 들어 `enqueue(10)`, `dequeue()`, `add(7)`, `remove(3)`처럼 메서드 이름과 인자값이 들어간다.

10. 여러 스레드가 같은 current node(현재 노드) 뒤에 서로 다른 candidate node(후보 노드)를 붙이려고 할 수 있다. `Consensus decideNext`는 그 후보들 중 정확히 하나를 다음 log node(로그 노드)로 합의하기 위해 필요하다. 이것이 없으면 스레드마다 다른 next를 붙였다고 생각해 log(로그)의 순서가 갈라지고, 공유 객체의 상태를 하나로 재현할 수 없게 된다.
